# Личная CRM

Список людей, которых я знаю лично: кто это, откуда знакомы, телефон, почта и заметки о разговорах.

## Запуск

Нужны Docker Desktop, Node.js 20.9+ и pnpm.

### 1. База данных и почтовая заглушка (Docker)

1. Создать файл `.env` по образцу `.env.example` и заполнить значения.
   `.env` хранит пароли и в git не попадает. Приложение берёт подключение к базе из этих же переменных.

   Строки для входа:

   | Строка | Что это | Значение на компьютере |
   |---|---|---|
   | `OWNER_EMAIL` | ваша почта: ваши контакты, заметки и группы, которые были до появления входа, и демо-данные | ваша почта |
   | `BETTER_AUTH_SECRET` | секрет, которым подписан вход; длинная случайная строка | сгенерировать командой ниже |
   | `BETTER_AUTH_URL` | адрес приложения: на него ведёт ссылка из письма | `http://localhost:3000` |
   | `SMTP_URL` | куда отправлять письма | `smtp://127.0.0.1:1025` — почтовая заглушка Mailpit |

   Секрет (выводит случайную строку, её вставить после `BETTER_AUTH_SECRET=`):

   ```
   node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
   ```

2. Запустить базу и почтовую заглушку (из папки проекта):

   ```
   docker compose up -d --wait
   ```

3. Проверить, что всё работает:

   ```
   docker compose ps
   ```

   У `postgres` и `mailpit` в колонке STATUS должно быть `healthy`.

Остановить: `docker compose stop`. Данные базы при этом сохраняются.

**Почтовая заглушка Mailpit.** Письма со ссылкой для входа на компьютере никуда не уходят: их ловит Mailpit. Все пойманные письма — на странице http://localhost:8025, оттуда берётся ссылка для входа. Войти можно под любым адресом, даже несуществующим. Письма хранятся, пока Mailpit не перезапущен.

### 2. Приложение

Один раз после скачивания проекта:

```
pnpm install
pnpm db:migrate
```

`db:migrate` создаёт в базе таблицы. Повторный запуск безопасен: уже применённые изменения пропускаются.

Миграциям нужна строка `OWNER_EMAIL`: всё, что уже есть в базе (контакты, заметки, группы, в том числе пять готовых групп), становится данными пользователя с этой почтой. Без неё или с неверной почтой `db:migrate` падает и база остаётся прежней. `drizzle-kit` при этом пишет только `Command failed with exit code 1` — проверьте строку `OWNER_EMAIL` в `.env`.

Тестовые данные (1000 контактов с заметками и группами) — по желанию:

```
pnpm db:seed
```

Скрипт пишет их на пользователя с почтой из `OWNER_EMAIL` (если такого ещё нет — создаёт), в его группы. Если у этого пользователя уже есть контакты, скрипт ничего не делает. Чтобы увидеть демо-данные, войдите под этой почтой.

Запуск для работы:

```
pnpm build
pnpm start
```

Запуск во время разработки (изменения в коде видны сразу):

```
pnpm dev
```

После запуска открыть http://localhost:3000. Остановить приложение — `Ctrl+C` в окне, где оно запущено.

## Как проверить, что всё работает

### Вход

1. Открыть http://localhost:3000 — открылась страница входа: слева «Люди, которых знаю лично», справа панель «Вход». В шапке только «Личная CRM».
2. Ввести свою почту (из `OWNER_EMAIL`) → «Получить ссылку». Под кнопкой «Ссылка для входа отправлена на …». Ввести «anna@» → под полем «Проверь адрес почты».
3. Открыть http://localhost:8025 — там письмо «Вход в Личную CRM» от «Личная CRM». Открыть его, нажать «Войти» (или скопировать ссылку из строки «Кнопка не открывается?» в браузер).
4. Открылся список ваших контактов. В шапке — ваша почта и «Выйти».
5. Открыть ту же ссылку из письма ещё раз — «Ссылка устарела, запроси новую» и кнопка «На страницу входа».
6. Открыть приложение в другом браузере (или в окне инкогнито) и войти под другой почтой, например `test@example.com`, — пустой список и подсказка «Добавь первый контакт», на странице «Группы» — «Групп пока нет». Добавить контакт. В первом браузере его нет.
7. В первом браузере скопировать адрес своего контакта и открыть во втором — «Контакт не найден».
8. Нажать «Выйти» — страница входа. Адрес любой страницы приложения снова ведёт на вход. В другом браузере вход остался.

**С телефона.** Ссылка в письме ведёт на `BETTER_AUTH_URL`, а `localhost` на телефоне — это сам телефон, поэтому ссылка с компьютера там не откроется. Для проверки с телефона: временно указать в `.env` адрес компьютера в домашней сети, например `BETTER_AUTH_URL=http://192.168.1.10:3000`, запустить `pnpm dev -H 0.0.0.0`, на телефоне открыть этот адрес, запросить ссылку, а письмо открыть в Mailpit на компьютере и перепечатать или переслать ссылку на телефон. Потом вернуть `http://localhost:3000`. Если включён VPN, телефон может не видеть компьютер — на время проверки выключить VPN.

### Контакты

1. Открыть http://localhost:3000 и войти — виден список ваших контактов и их количество.
2. «Добавить контакт» → заполнить имя → «Добавить». Контакт подсвечен в списке.
3. Набрать часть имени в поиске — список сразу отфильтруется. Открыть контакт.
4. Написать заметку → «Добавить заметку» (или Ctrl+Enter). Обновить страницу — заметка на месте.
5. Открыть тот же адрес в другом браузере и войти под той же почтой — те же контакты и заметки.
6. Открыть контакт → «Удалить» → в окне подтверждения «Удалить». Открылся список с уведомлением «Контакт удалён», контакта в нём нет, число контактов уменьшилось на 1.

### Пора связаться

7. Открыть контакт, у которого больше недели не было заметок (или без заметок, добавленный больше недели назад) → «Изменить» → в «Как часто общаться» выбрать «Раз в неделю» → «Сохранить». На странице контакта строка «Как часто общаться»: «Раз в неделю · пора было N дней назад» (или «пора сегодня»).
8. Открыть главную. Над поиском блок «Пора связаться», в нём этот контакт: «раз в неделю · последний раз N дней назад» или «ещё не общались». Сверху самые просроченные, сразу видны первые три. Если контакта среди них нет — нажать «Показать всех», он будет ниже. «Свернуть» снова оставляет первых трёх.
9. Нажать на этот контакт в блоке, написать заметку → «Добавить заметку». Строка «Как часто общаться» сразу показывает «следующий раз до …» — через неделю от сегодня. Вернуться на главную — контакта в блоке больше нет.
10. У другого контакта в блоке нажать галочку справа («Уже связался»). Под строкой открылось поле заметки, страница контакта не открылась. Ничего не писать, нажать «Сохранить». Контакт ушёл из блока, вверху уведомление «Заметка сохранена» с кнопкой «Отменить». На странице контакта первая заметка — «Связались».
11. С ещё одним контактом из блока сделать то же самое, но в течение 5 секунд нажать «Отменить» в уведомлении. Контакт вернулся в блок на своё место, на его странице заметки «Связались» нет.
12. Набрать имя в поиске — блок «Пора связаться» скрыт. Очистить поиск — блок снова виден.

Тестовые данные (`pnpm db:seed`) задают частоту примерно трети контактов, поэтому на них блок сразу заполнен.

13. Выбрать на главной группу (шаг 22). В блоке «Пора связаться» остались только контакты этой группы. Если в выбранной группе никому не пора, блока нет. Нажать «Все» — блок снова прежний.

### Группы

14. В шапке нажать «Группы» (с главной и со страницы контакта). Открылась страница «Группы»: у владельца данных (`OWNER_EMAIL`) пять готовых групп — «Семья», «Друзья», «Знакомые», «Теннис», «Аналитики», у каждой число контактов. У нового пользователя групп нет.
15. В поле «Новая группа» ввести «Коллеги» → «Добавить». «Коллеги» — последняя в списке, поле пустое. Ввести «коллеги» ещё раз → «Такая группа уже есть». Пустое поле → «Укажите название группы».
16. У «Коллеги» нажать «Переименовать», написать «Соседи» → «Сохранить». Группа переименована, место в списке то же. «Переименовать» → изменить текст → «Отмена» (или Esc): название прежнее. Переименовать в «друзья» → «Такая группа уже есть».
17. У «Соседи» нажать «Удалить». В окне написано, что контактов в группе нет. «Отмена» — группа на месте. «Удалить» → «Удалить»: группы в списке нет.
18. Открыть контакт → «Изменить». В поле «Группы» отметить «Друзья» и «Теннис» → «Сохранить». Снова «Изменить»: обе группы отмечены. Снять «Теннис» → «Сохранить»: осталась только «Друзья».
19. «Добавить контакт». В поле «Группы» под отметками ввести «Коллеги» и нажать «Добавить» (или Enter — форма при этом не отправляется): «Коллеги» появилась отмеченной. Ввести «семья» → «Добавить»: отметилась готовая «Семья», новой группы нет. Оставить имя из одних пробелов → «Добавить»: ошибка имени, а «Семья» и «Коллеги» остались отмеченными.
20. Заполнить имя → «Добавить». На странице «Группы» «Коллеги» — последняя, в ней 1 контакт. Начать ещё один контакт, завести группу «Партнёры» и нажать «Отмена»: на странице «Группы» «Партнёров» нет.
21. Открыть этот контакт. В строке «Группы» (после «Откуда знакомы») — «Семья, Коллеги», каждое название — ссылка. Нажать «Коллеги»: открылась главная с выбранной «Коллеги». У контакта без групп в строке «Группы» прочерк.
22. На главной над «Пора связаться» — кнопки «Все» и группы. Нажать «Теннис»: кнопка выделена, в списке только контакты из «Теннис», под заголовком «Найдено N из M». В строках мелко написаны группы контакта. Нажать «Семья», потом «Назад» в браузере: снова выбрана «Теннис».
23. При выбранной «Теннис» ввести в поиск часть имени: ищет только внутри группы, «Теннис» остаётся выбранной. Очистить поиск — группа по-прежнему выбрана. Выбрать другую группу, пока в поиске есть текст: текст остался. Выбрать группу, в которой нет контактов: «В группе «…» пока никого нет».
24. Скопировать адрес главной с выбранной группой и открыть его в новой вкладке: та же группа. Удалить эту группу на странице «Группы» и открыть сохранённый адрес: главная с выбранным «Все». Удалить все группы: на главной нет ряда кнопок, список выглядит как раньше, а на странице «Группы» написано «Групп пока нет» и есть форма добавления.

Тестовые данные (`pnpm db:seed`) раскладывают контакты по группам: у примерно двух третей есть одна или две группы, родственники — в «Семья», тренер по теннису — в «Теннис».

## Тесты

Тесты проверяют серверную часть на настоящей базе и с настоящим Better Auth. Письма в них не уходят, кроме одного теста отправки: он шлёт письмо в Mailpit. Сначала запустить базу и Mailpit (если ещё не запущены):

```
docker compose up -d --wait
```

Потом:

```
pnpm test
```

Перед прогоном создаётся отдельная тестовая база рядом с рабочей: к имени из `POSTGRES_DB` добавляется `_test`. В ней применяются все миграции, и перед каждым тестом таблицы очищаются. Рабочие данные не трогаются: тесты отказываются работать с базой, имя которой не кончается на `_test`.

`pnpm test:watch` — то же, но тесты перезапускаются при правках.

### e2e-тесты

Открывают приложение в настоящем браузере и проходят сценарии как пользователь. Нужна запущенная база (как выше) и один раз браузер:

```
pnpm exec playwright install chromium
```

Запуск:

```
pnpm test:e2e
```

Тест сам пересоздаёт тестовую базу (`_test`, как у `pnpm test`), собирает приложение (`pnpm build`) и запускает его на порту 3100 с этой базой. Рабочая база не трогается. Не запускать вместе с `pnpm dev` и `pnpm test`: сборка пересоздаёт папку `.next`, а оба набора тестов используют одну тестовую базу.

Тесты входят в приложение как человек: запрашивают ссылку в форме, берут письмо из Mailpit и открывают ссылку. Нужны запущенный Mailpit и строки `BETTER_AUTH_SECRET` и `SMTP_URL` в `.env`; без них тест сразу скажет, какой строки нет.

При падении теста в папке `test-results` остаётся трассировка: `pnpm exec playwright show-trace <путь к trace.zip>`.

### Проверка формата и типов

```
pnpm lint            # ESLint
pnpm typecheck       # TypeScript
pnpm format:check    # Prettier: только проверить
pnpm format          # Prettier: сам поправить файлы
```

### CI

На каждый PR в main GitHub Actions (`.github/workflows/ci.yml`) гоняет три проверки: «Lint, format, types», «Vitest and Playwright» (на настоящем Postgres и Mailpit, секрет входа — случайный на каждый прогон) и «Build image» (собирается образ, но не публикуется). Пока они не зелёные, PR в main не вливается. Если упали e2e-тесты, трассировки лежат в артефакте `playwright-traces` на странице запуска.

## Изменения схемы базы

Таблицы описаны в `src/db/schema.ts`. После правки схемы:

```
pnpm db:generate
pnpm db:migrate
```

Первая команда создаёт файл миграции в папке `drizzle/`, вторая применяет его к базе.

Таблицы входа (пользователи, сеансы, ссылки) — в `src/db/auth-schema.ts`, их создаёт CLI Better Auth. После обновления Better Auth их стоит пересоздать командой из `scripts/better-auth-cli.ts` и вернуть правки, описанные в начале `src/db/auth-schema.ts`.

## Подготовка сервера (один раз)

Скрипт `deploy/server-setup/setup.sh` готовит сервер к выкатке:

- ставит Docker из официального репозитория. Порты контейнеров открываются только на 127.0.0.1, снаружи к ним не попасть. Логи контейнеров ограничены по размеру;
- создаёт пользователя `deploy`: под ним GitHub Actions выкатывает приложение. Пароля и sudo у него нет, только SSH-ключи и доступ к Docker. Доступ к Docker равен правам root, поэтому ключи берегите;
- создаёт папки приложения: `/home/deploy/personal-crm` (прод) и `/home/deploy/personal-crm-staging` (тест-стенд);
- ставит nginx: на whobook.ru заглушка, app.whobook.ru передаёт запросы приложению, test-app.whobook.ru — приложению тест-стенда. Пока приложение не запущено, там видна страница «Приложение временно недоступно». http перенаправляется на https;
- закрывает test-app.whobook.ru логином и паролем. Если пароля ещё нет, спрашивает логин и пароль (пароль не виден на экране, не короче 12 символов). На сервере хранится только хеш пароля;
- получает сертификаты Let's Encrypt: один на whobook.ru и app.whobook.ru, отдельный на test-app.whobook.ru. Продлеваются сами, по таймеру `certbot.timer`.

Перед запуском DNS-записи всех трёх доменов должны указывать на сервер. Повторный запуск безопасен: готовые шаги пропускаются, файлы, созданные не этим скриптом, не трогаются.

Ключи для входа под `deploy` скрипт берёт из файла `deploy-authorized_keys` рядом с собой. В git этот файл не хранится, его кладут на сервер отдельно. В нём две строки: публичная часть ключа деплоя (с пометкой `restrict`: только команды, без терминала) и ваш личный публичный ключ.

Запуск из папки проекта в PowerShell (спросит пароль sudo):

```
scp -r deploy/server-setup crm:~/
ssh -t crm 'sudo bash ~/server-setup/setup.sh <почта> 2>&1 | tee ~/server-setup/setup.log'
```

После этого — один раз создать на сервере файл с паролем базы. Войти под `deploy` (`crm-deploy` — запись в `~/.ssh/config`):

```
ssh crm-deploy
```

и уже на сервере выполнить:

```
set -o noclobber; umask 077
{ echo POSTGRES_USER=crm; echo POSTGRES_DB=crm; echo "POSTGRES_PASSWORD=$(openssl rand -hex 24)"; } > ~/personal-crm/.env
exit
```

Пароль генерируется случайный и на экран не выводится. Файл доступен только владельцу (права 600). Если файл уже есть, команда его не перезапишет.

### Вход: письма через Resend и строки `.env` на сервере

Письма для входа сервер отправляет через Resend, от адреса `noreply@mail.crm.whobook.ru`. Настроить один раз, до выкатки входа.

1. Зарегистрироваться на https://resend.com.
2. Domains → Add Domain → `mail.crm.whobook.ru`. Resend покажет DNS-записи (MX и TXT для отправки, TXT для подписи DKIM, по желанию DMARC). Добавить их у регистратора домена `whobook.ru` и дождаться, пока у домена в Resend будет статус «Verified».
3. API Keys → Create API Key: право «Sending access», домен `mail.crm.whobook.ru`. Ключ показывается один раз — скопировать.
4. Дописать строки в `.env` на сервере. Войти под `deploy`:

   ```
   ssh crm-deploy
   ```

   и на сервере выполнить, подставив свою почту (ей достанутся все контакты, которые уже есть на сервере):

   ```
   umask 077
   { echo "OWNER_EMAIL=<ваша почта>"; echo "BETTER_AUTH_SECRET=$(openssl rand -base64 32)"; } >> ~/personal-crm/.env
   read -rs -p "Ключ Resend: " key; echo; echo "SMTP_URL=smtps://resend:${key}@smtp.resend.com:465" >> ~/personal-crm/.env; unset key
   exit
   ```

   Секрет генерируется случайный, ключ Resend вводится без вывода на экран и в историю команд не попадает. Права файла остаются 600.

Адрес приложения (`BETTER_AUTH_URL`) не секрет: у каждого окружения он свой и задан в `deploy/lib.sh` (прод — `https://app.whobook.ru`, тест-стенд — `https://test-app.whobook.ru`). Ссылка во входном письме ведёт на этот адрес, то есть туда, где запросили вход. Если в `.env` нет хотя бы одной из строк `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `SMTP_URL`, выкатка останавливается на первом шаге, до бэкапа, ничего не меняя, и пишет, какой строки нет.

### `.env` тест-стенда

У тест-стенда свой `.env`: свой пароль базы, свой секрет входа и свой ключ Resend. Настроить один раз, до первой выкатки на стенд.

1. В Resend: API Keys → Create API Key, название, например, `staging`, право «Sending access», домен `mail.crm.whobook.ru`. Скопировать ключ. Письма со стенда настоящие, с того же адреса `noreply@mail.crm.whobook.ru`.
2. Войти под `deploy`:

   ```
   ssh crm-deploy
   ```

   и на сервере выполнить, подставив ту же почту, что в `OWNER_EMAIL` на проде:

   ```
   set -o noclobber; umask 077; mkdir -p ~/personal-crm-staging
   { echo POSTGRES_USER=crm; echo POSTGRES_DB=crm; echo "POSTGRES_PASSWORD=$(openssl rand -hex 24)"; echo "OWNER_EMAIL=<ваша почта>"; echo "BETTER_AUTH_SECRET=$(openssl rand -base64 32)"; } > ~/personal-crm-staging/.env
   read -rs -p "Ключ Resend для стенда: " key; echo; echo "SMTP_URL=smtps://resend:${key}@smtp.resend.com:465" >> ~/personal-crm-staging/.env; unset key
   exit
   ```

   Пароль базы и секрет генерируются случайные, ключ вводится без вывода на экран. Файл доступен только владельцу (права 600). Если файл уже есть, первая строка его не перезапишет.

## Выкатка

Выкатка автоматическая: каждый push в `main` выкатывает новую версию сразу в два окружения — на тест-стенд https://test-app.whobook.ru и на прод https://app.whobook.ru. Это один и тот же образ. Стенд и прод выкатываются параллельно и друг от друга не зависят: упал стенд — прод всё равно выкатится, и наоборот.

Что происходит (GitHub → вкладка Actions → Deploy):

1. GitHub Actions собирает образ приложения. Тег образа — SHA коммита. Образ кладётся в GHCR: `ghcr.io/pashke/personal-crm`.
2. Дальше две задачи: «Deploy to the test stand» и «Deploy to prod». Каждая заходит на сервер под `deploy`, копирует папку `deploy/` в папку своего окружения и запускает `deploy/deploy.sh staging` или `deploy/deploy.sh prod`:
   - только на проде: снимает бэкап базы (см. «Бэкапы и восстановление»). Если бэкап не получился, выкатка останавливается, работает старая версия;
   - только на стенде: если база стенда пустая (первая выкатка), заливает в неё копию самого свежего бэкапа прода;
   - скачивает новый образ;
   - разовый контейнер из этого образа применяет миграции базы и завершается. Если миграции упали, новая версия не стартует, работает старая;
   - запускает новую версию;
   - smoke-проверка: `/health` должен ответить 200 и напрямую, и через nginx;
   - только на проде: удаляет образы, которые больше не нужны. Остаются текущая и предыдущая версии прода и текущая версия стенда.
3. Две выкатки в одно окружение одновременно не идут: вторая ждёт, пока закончится первая (и в GitHub, и на сервере).
4. Если что-то упало, задача в Actions красная, и GitHub присылает письмо. Сама выкатка ничего не откатывает.

Проверить после выкатки:

- в Actions последний запуск Deploy зелёный, обе задачи;
- https://app.whobook.ru/health показывает `{"status":"ok"}`;
- https://app.whobook.ru открывается (без входа — страница входа), вход по письму работает, изменения на месте;
- то же на https://test-app.whobook.ru (сначала браузер спросит логин и пароль стенда).

База у каждого окружения своя, в Docker: контейнер `postgres` проекта `prod`, том `prod_postgres-data`; на стенде — проекта `staging`, том `staging_postgres-data`. Данные переживают выкатки.

### Откат прода (только вручную)

```
ssh crm-deploy personal-crm/deploy/rollback.sh
```

Возвращает последнюю рабочую версию. Если упала последняя выкатка, это версия до неё, иначе предыдущая. Другая версия: `rollback.sh <sha коммита>`, её образ должен быть на сервере. Откат — это обычная выкатка старой версии, поэтому он тоже сначала снимает бэкап базы. Изменения базы откат не отменяет: старая версия работает с текущей базой. Вернуть и базу — см. «Восстановление базы».

### Полезные команды

Первый параметр `compose.sh` — окружение: `prod` или `staging`.

```
ssh crm-deploy personal-crm/deploy/compose.sh prod ps                   # что запущено на проде
ssh crm-deploy personal-crm/deploy/compose.sh prod logs --tail 100 app  # логи приложения прода
ssh crm-deploy cat personal-crm/state/current-version                   # какая версия работает на проде
ssh crm-deploy ls -lh personal-crm/backups                              # бэкапы базы прода
ssh crm-deploy personal-crm/deploy/compose.sh prod run --rm seed        # тестовые данные (только в пустую базу)
```

### Логи

Логи контейнеров читаются через `compose.sh`:

```
ssh crm-deploy personal-crm/deploy/compose.sh prod logs --tail 200 app                  # последние 200 строк приложения прода
ssh crm-deploy personal-crm/deploy/compose.sh prod logs --since 1h postgres             # база прода за последний час
ssh crm-deploy personal-crm-staging/deploy/compose.sh staging logs --tail 200 app       # приложение стенда
ssh crm-deploy personal-crm-staging/deploy/compose.sh staging logs --follow app         # стенд в реальном времени (выход — Ctrl+C)
```

Сейчас логи хранятся у каждого контейнера, не больше 3 файлов по 10 МБ, и пропадают вместе с контейнером (при каждой выкатке приложение — новый контейнер).

## Тест-стенд

https://test-app.whobook.ru — копия приложения на том же сервере, для проверки перед продом. Каждый push в `main` выкатывает туда ту же версию, что и на прод.

- **Пароль.** Весь адрес закрыт логином и паролем, их спрашивает браузер. Без пароля пускает только сам сервер — для smoke-проверки при выкатке. Приложение пароль стенда не видит. Сменить логин или пароль (спросит пароль sudo, потом новые логин и пароль; работает сразу):

  ```
  ssh -t crm sudo bash ~/server-setup/staging-password.sh
  ```

  Если папки `~/server-setup` на сервере нет, сначала скопировать её: `scp -r deploy/server-setup crm:~/`.

- **Своё всё.** Своя папка `/home/deploy/personal-crm-staging`, свой `.env` (см. «`.env` тест-стенда»), своя база, свой сертификат, приложение на 127.0.0.1:3001. Вход по письму настоящий, ссылка ведёт на https://test-app.whobook.ru. Кука входа — только для test-app.whobook.ru: вход на стенде не входит в прод и наоборот.
- **Память ограничена**, чтобы стенд не отнял её у прода: приложение и разовые контейнеры (миграции) — 512 МБ, база — 256 МБ. У прода лимитов нет. Значения — в `deploy/lib.sh`.
- **База — копия прода.** Первая выкатка видит пустую базу стенда и заливает в неё самый свежий бэкап прода, потом применяет миграции. Дальше база стенда живёт своей жизнью: изменения на стенде на прод не попадают, изменения на проде — на стенд.
- **Бэкапов у стенда нет.**

### Пересоздать базу стенда

Если данные на стенде испортились или нужна свежая копия прода. Удаляет базу стенда и заливает в неё самый свежий бэкап прода (копии `restore` не берёт), потом применяет миграции текущей версии стенда и запускает её снова. Прод не трогает.

```
ssh -t crm-deploy personal-crm-staging/deploy/refresh-staging-db.sh
```

Скрипт покажет, какой бэкап и какую базу заменит, и спросит `yes`. Без терминала (так запускает агент, после вашего согласия) — с флагом `--yes`, без вопроса. Свежий бэкап прода появляется при каждой выкатке на прод.

Пока скрипт работает, выкатка на стенд ждёт его. Если он упал на полпути — запустить ещё раз.

### Откат стенда

Отдельного скрипта нет — выкатить на стенд нужную версию, её образ должен быть на сервере:

```
ssh crm-deploy personal-crm-staging/deploy/deploy.sh staging <sha коммита>
ssh crm-deploy docker image ls ghcr.io/pashke/personal-crm   # какие образы есть
```

## Бэкапы и восстановление

### Бэкапы

Каждая выкатка на прод (и каждый откат прода) первым делом снимает бэкап базы прода. У тест-стенда бэкапов нет. Бэкапы лежат на сервере в `/home/deploy/personal-crm/backups/`. Читать их может только пользователь `deploy`, в них личные данные.

Имя файла — время и версия приложения, которая работала до выкатки:

```
2026-11-04_123005_deploy_52a316c...dump
```

- `2026-11-04_123005` — дата и время, UTC (по Москве +3 часа);
- `deploy` — снят выкаткой. `restore` — копия, которую снял скрипт восстановления перед заменой базы;
- дальше полный SHA коммита: с этой версией приложения база и была.

Хранятся 10 последних бэкапов выкаток, более старые удаляются сами. Копии `restore` сами не удаляются, лишние удаляйте вручную:

```
ssh crm-deploy rm personal-crm/backups/<файл>
```

Бэкапы лежат на том же сервере: от неудачной миграции или ошибки они спасают, от потери самого сервера — нет.

### Восстановление базы

Только вручную, скриптом `restore.sh`. Он заменяет всю базу прода содержимым бэкапа. Всё, что записано в базу после бэкапа, из неё пропадёт, но останется в копии, которую скрипт снимает перед заменой.

1. Посмотреть бэкапы и выбрать файл:

   ```
   ssh crm-deploy ls -lh personal-crm/backups
   ```

2. Запустить (ключ `-t` обязателен: скрипт ждёт ответа):

   ```
   ssh -t crm-deploy personal-crm/deploy/restore.sh <имя файла>
   ```

3. Скрипт проверит, что файл — целый бэкап, и покажет:
   - какой файл загрузит: размер, когда записан, с какой версией приложения снят;
   - какую базу удалит: имя, контейнер, размер;
   - какая версия приложения останется работать.

   Ввести `yes` — пойдёт восстановление. Любой другой ответ — выход, ничего не изменено.

4. Дальше скрипт сам:
   - снимает копию текущей базы (`..._restore_...dump` в той же папке);
   - останавливает приложение;
   - удаляет базу, создаёт пустую и загружает в неё бэкап;
   - запускает ту же версию приложения и проверяет `/health`.

   В конце пишет `RESTORED` и путь к копии.

Версию приложения restore не меняет и миграции не запускает. Если бэкап снят с другой версией, скрипт об этом предупредит.

Пока restore работает или ждёт ответа, выкатка ждёт его (до 10 минут). Во время выкатки restore не запустится.

### Вернуть всё как было до неудачной выкатки

Например, новая версия испортила данные.

**Выкатка входа — только так.** Она меняет базу: у контактов и групп появляется владелец, а название группы становится уникальным только среди групп одного пользователя. Версия до входа на такой базе работала бы неправильно: показывала бы всем все контакты. Поэтому откатывать выкатку входа можно только вместе — версию приложения (шаг 1) и базу из бэкапа, снятого перед этой выкаткой (шаг 2). Один `rollback.sh` без восстановления базы здесь не годится.

1. Откатить приложение на версию из имени бэкапа:

   ```
   ssh crm-deploy personal-crm/deploy/rollback.sh <sha из имени бэкапа>
   ```

   Её образ должен быть на сервере, хранятся текущий и предыдущий образы прода и текущий образ стенда.

2. Восстановить базу из этого бэкапа (как выше). Откат сам снимет ещё один бэкап, нужен именно тот, что был снят перед неудачной выкаткой.

### Если restore упал

Скрипт ничего не откатывает сам. Он пишет, на каком шаге упал и где лежит копия базы, снятая перед заменой.

- Упал до удаления базы — ничего не изменилось, приложение работает.
- Упал после удаления базы (или пропала связь) — приложение остановлено, база может быть пустой. Вернуть прежнюю базу — тем же скриптом из копии. Её имя скрипт пишет в сообщении об ошибке. Если сообщения не видно (пропала связь), это самый новый файл `..._restore_...dump`:

  ```
  ssh -t crm-deploy personal-crm/deploy/restore.sh <файл копии>
  ```

### Настройки в GitHub

Settings → Secrets and variables → Actions:

- секрет `DEPLOY_SSH_KEY` — приватная часть ключа деплоя;
- переменные `DEPLOY_HOST` (адрес сервера), `DEPLOY_USER` (`deploy`), `DEPLOY_KNOWN_HOSTS` (отпечаток сервера: так GitHub убеждается, что подключился именно к нему).
