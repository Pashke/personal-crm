# Design

## Context

Зачем - см. proposal.md, что должно работать - см. specs/monitoring/spec.md.

Что есть сейчас (проверено на сервере 2026-11-14):

- VPS: 1 ядро, 1,8 ГБ памяти (свободно около 1 ГБ), swap 900 МБ в zram, диск 40 ГБ (свободно 34 ГБ), нагрузка около 0. Ubuntu 24.04, Docker 29, nginx 1.24 и certbot из Ubuntu.
- Проекты compose `prod` и `staging` из одного `deploy/compose.yaml`: окружение выбирает `use_env` в `deploy/lib.sh`. Порты приложений опубликованы только на 127.0.0.1 (3000, 3001), у базы порта нет: до неё доходят только контейнеры своего проекта. У стенда лимиты памяти (приложение 512 МБ, база 256 МБ), у прода нет.
- `daemon.json`: опубликованные порты по умолчанию на 127.0.0.1. ufw пропускает только 22, 80, 443. Порты, опубликованные Docker, обходят ufw, а сокеты контейнеров в сети хоста нет: их ufw фильтрует.
- nginx: сайты из `deploy/server-setup/nginx/sites/`, файлы с пометкой `managed-by` ставит `setup.sh` (root, запускает пользователь). Стенд закрыт basic auth (`staging-password.sh`), запросы с 127.0.0.1 проходят без пароля: так `check_health` в `lib.sh` проверяет стенд через nginx (`--resolve test-app.whobook.ru:443:127.0.0.1`).
- Сертификаты: `whobook.ru` (whobook.ru и app.whobook.ru) и `test-app.whobook.ru`, продление по `certbot.timer`. Let's Encrypt больше не присылает писем об окончании.
- Ночной бэкап: `personal-crm-backup.timer` → `backup.sh` (пользователь `deploy`) → `~/personal-crm/backups/<UTC>_daily_<sha>.dump`. Файл пишется как `.partial` и переименовывается только после проверки, поэтому время изменения готового `*_daily_*.dump` - это время удачного бэкапа.
- Выкатка: `ci-deploy.sh` копирует `deploy/` (без `server-setup` и `ci-*.sh`) в папку окружения целиком, удаляя старую копию (`rm -rf deploy; mv deploy.new deploy`), и запускает там скрипт. Deploy prod запускает только человек.
- Логи наших контейнеров идут в journald (`tag={{.Name}}`, поля проекта и сервиса), `logs.sh` их читает; rsyslog не копирует строки с именами `^(prod|staging)-(app|postgres|migrate|seed)-` в `/var/log/syslog`.
- Письма приложение шлёт через Resend по SMTP (`smtps://…@smtp.resend.com:465`) с адреса `noreply@mail.crm.whobook.ru`. Ключи - в `.env` окружений.
- Репозиторий публичный.

## Goals / Non-Goals

**Goals:**

- Мониторинг живёт отдельно от приложения: его поломка, обновление или выключение не трогает прод и тест-стенд.
- Всё, что можно, задано файлами в репозитории: страница с графиками, правила тревог, текст писем. Изменения - через PR и Deploy prod, как у выкатки.
- Ничего из мониторинга не слушает внешние адреса: наружу выходит только nginx.

**Non-Goals:**

- Отдельный тест-стенд для мониторинга: он один на сервер и смотрит на оба окружения.
- Своя роль только для чтения в базе прода для сборщика показателей (см. риски).
- Правка правил тревог через интерфейс Grafana: правила из файлов там только для чтения, заглушить тревогу можно.

## Decisions

### 1. Отдельный проект compose `monitoring` со своей папкой

`/home/deploy/personal-crm-monitoring/`: свой `.env` (права 600), своя копия `deploy/`, папка `config-<время>/` с текущими настройками, папка `textfile/` для показателя бэкапа. Файл `deploy/monitoring/compose.yaml`, проект `-p monitoring`, сервисы `grafana`, `prometheus`, `node-exporter`, `blackbox`. Тома `grafana-data` (пользователь, заглушки, состояние тревог) и `prometheus-data` (показатели).

- Альтернатива: сервисы мониторинга в `deploy/compose.yaml` рядом с приложением. Отказались: мониторинг один на сервер, а файл - на окружение; при восстановлении базы и выкатке мониторинг пересоздавался бы вместе с приложением.
- Альтернатива: ставить мониторинг из `setup.sh` (root). Отказались: каждую правку тревоги пришлось бы выкатывать пользователю через sudo.

### 2. Сеть хоста, всё слушает только 127.0.0.1

Контейнеры мониторинга работают в сети хоста (`network_mode: host`), каждый слушает только 127.0.0.1: Grafana 3002, Prometheus 9090, node_exporter 9100, blackbox_exporter 9115. Даже если адрес где-то задан неверно, ufw закрывает эти порты снаружи.

Почему сеть хоста:

- Prometheus достаёт сборщики и порт сборщика базы прода (опубликован на 127.0.0.1 хоста) без лишних сетей;
- проверка стенда идёт с 127.0.0.1, и nginx пускает её без пароля, как `check_health`;
- node_exporter и так нужен вид на хост.

- Альтернатива: своя сеть Docker и опубликованные порты. Отказались: из такой сети не достать 127.0.0.1 хоста, а запросы к стенду шли бы не с 127.0.0.1 и упирались бы в пароль стенда, который пришлось бы хранить в мониторинге.

### 3. Сборщик показателей базы - рядом с базой прода

Сервис `postgres-exporter` в `deploy/compose.yaml` с профилем `monitoring`. `use_env prod` включает профиль (`COMPOSE_PROFILES=monitoring`), `use_env staging` - нет, поэтому на стенде его нет. Он в сети проекта `prod` и ходит к `postgres:5432` с логином и паролем из `.env` прода: второй копии пароля нет. Порт `127.0.0.1:9187`, лимит памяти. `deploy.sh prod` поднимает его после приложения. Если он не поднялся, выкатка не падает: смок приложения уже прошёл, а молчание сборщика заметит тревога «нет данных».

- Альтернатива: сборщик в проекте `monitoring`, подключённый к сети `prod_default` и читающий `.env` прода. Отказались: связывает два проекта по имени сети и по чужому `.env`; если сеть пересоздать, сборщик теряет базу до перезапуска.

### 4. Проверка сайтов и сертификатов - blackbox_exporter

Prometheus раз в 30 секунд просит blackbox проверить:

- прод: `https://app.whobook.ru/health`, как посетитель: DNS, сертификат, nginx, приложение, база (`/health` проверяет базу);
- стенд: `https://127.0.0.1/health` с заголовком `Host: test-app.whobook.ru` и тем же именем в TLS (SNI) - nginx пускает 127.0.0.1 без пароля;
- сертификаты: TLS-соединение с `app.whobook.ru:443`, `test-app.whobook.ru:443`, `grafana.whobook.ru:443`, без HTTP-запроса - пароль Grafana и стенда не мешает. Сертификат лендинга общий с app.whobook.ru.

### 5. Время последнего ночного бэкапа - файл для node_exporter

Функция в `lib.sh` находит самый новый `*_daily_*.dump` в папке бэкапов и пишет его время в `textfile/backup.prom` (через временный файл и переименование). node_exporter читает папку `textfile/` и отдаёт показатель `personal_crm_daily_backup_last_success_timestamp_seconds`.

- `backup.sh` вызывает её после удачного бэкапа. Если записать не вышло, бэкап остаётся удачным, в лог идёт предупреждение (тревога тогда сработает через 26 часов - это и нужно).
- `monitoring.sh` вызывает её при каждом обновлении мониторинга: после первого запуска показатель уже есть, и письма «нет данных» о бэкапе нет.
- Альтернатива: состояние systemd-службы бэкапа. Отказались: node_exporter пришлось бы дать доступ к systemd хоста, а «служба удачна» не говорит, когда был последний бэкап.
- Альтернатива: Pushgateway. Отказались: ещё один сервис ради одного числа.

### 6. Тревоги и письма - сама Grafana

Правила тревог, точка отправки (почта), политика отправки и шаблоны писем - файлы provisioning в `deploy/monitoring/grafana/`. Alertmanager не нужен.

- Правила проверяются раз в минуту. Сколько ждать до письма - по таблице в proposal.md.
- Нет данных или ошибка запроса к Prometheus → правило срабатывает (`noDataState` и `execErrState` = Alerting) после того же ожидания, что и само правило. Значит, замолчавший сборщик или упавший Prometheus тоже дают письмо.
- Такую тревогу Grafana помечает аннотацией `grafana_state_reason` (`NoData` или `Error`), а `summary` и `description` оставляет от последней проверки с данными, со старыми цифрами (найдено на сервере 2026-11-15: письмо «мало памяти, свободно 876 МБ (49%)»). Поэтому у каждого правила есть текст `no_data`, а шаблон письма по этой пометке дописывает к теме «(нет данных)» и ставит в тело `no_data`.
- Политика: группировка по названию тревоги, повтор раз в сутки (`repeat_interval: 24h`), письмо при исправлении.
- Шаблон письма: тема «Тревога: <название>» или «Починилось: <название>», текст по-русски из описания правила (что случилось, значение, где смотреть), ссылка на страницу Grafana.
- Рамку письма (шапка «1 firing alert instance», «Grouped by», подпись «Sent by Grafana») Grafana 13 берёт из своего встроенного HTML-шаблона: ни `[smtp] content_types`, ни подмена файлов в `public/emails` на письма тревог не действуют (проверено на 13.3.1). Владелец решил (2026-11-15) оставить рамку как есть; отдельный сервис-пересыльщик ради полностью русского письма не заводим.
- Почта: SMTP Grafana на `smtp.resend.com:465` (TLS сразу, как у приложения), отправитель `noreply@mail.crm.whobook.ru`, имя «Личная CRM: мониторинг». Ключ Resend свой (`monitoring`). Адрес получателя Grafana берёт из переменной окружения в файле provisioning, значение - в `.env` мониторинга.
- Альтернатива: Prometheus + Alertmanager. Отказались: лишний контейнер и ещё одно место, где описаны правила.

### 7. Вход: пароль в nginx, Grafana доверяет nginx

- nginx: сайт `grafana.whobook.ru`, свой сертификат (`--cert-name grafana.whobook.ru`), basic auth со своим файлом паролей `/etc/nginx/whobook-grafana.htpasswd` (скрипт по образцу `staging-password.sh`, `setup.sh` спрашивает пароль, если его нет). nginx передаёт Grafana имя вошедшего в заголовке `X-WEBAUTH-USER`, удаляет заголовок `Authorization` (иначе Grafana проверит его сама и ответит 401), передаёт WebSocket для живых обновлений.
- Grafana: вход через прокси (`auth.proxy`) только с 127.0.0.1, форма входа, анонимный вход и регистрация выключены, новый пользователь получает роль Admin. Пароль встроенного admin - случайный, в `.env` мониторинга: им никто не входит, но он не стандартный. Сбор статистики и проверка обновлений Grafana выключены.
- Пока Grafana не запущена, nginx показывает страницу «временно недоступно», как у приложения.
- Альтернатива: только вход самой Grafana. Отказались: страница входа Grafana была бы открыта всему интернету, у Grafana бывали уязвимости входа; basic auth закрывает её целиком, как стенд.

### 8. Обновление - отдельный шаг Deploy prod

- `deploy-prod.yml`: новая задача «Update monitoring», после задачи выкатки, `if: ${{ !cancelled() }}` - и после красной выкатки и отката. Только вызов `bash deploy/ci-deploy.sh monitoring`.
- `ci-deploy.sh monitoring`: копирует `deploy/` в `~/personal-crm-monitoring/deploy` тем же способом, что и для окружений, и запускает `deploy/monitoring.sh`.
- `monitoring.sh` (как `deploy`, под своей блокировкой):
  1. проверяет `.env` мониторинга (есть, права 600, все строки есть) - иначе красный, ничего не тронуто;
  2. копирует `deploy/monitoring/` в новую папку `config-<время UTC>/` и проверяет настройки Prometheus (`promtool check config` из того же образа) - ошибка → красный, работающий мониторинг не тронут;
  3. пишет показатель бэкапа (решение 5);
  4. `docker compose -p monitoring up --detach --wait` с путём к новой папке настроек: путь сменился, поэтому compose пересоздаёт контейнеры;
  5. проверяет: Prometheus готов, Grafana отвечает, все цели Prometheus отвечают (ждёт до 60 секунд), в Grafana загружено каждое правило из `rules.yaml` (по uid; правила, созданные в самой Grafana, не мешают — сначала проверка считала все правила и падала из-за временного тестового правила, 2026-11-15);
  6. удаляет старые папки `config-*` и образы прошлых версий мониторинга, которые не использует ни один контейнер.
- Почему новая папка настроек: `ci-deploy.sh` удаляет старую `deploy/` целиком. Если бы контейнеры брали файлы прямо из `deploy/`, после копирования они увидели бы пустую папку, а Grafana удалила бы страницу с графиками. Своя папка на каждое обновление меняется атомарно: старые контейнеры работают со старой, пока их не пересоздали.
- Deploy staging мониторинг не трогает.
- Альтернатива: обновлять при Deploy staging, на каждый merge. Отказались: мониторинг - часть прода (общая память сервера, тревоги прода), а на прод изменения идут только кнопкой.

### 9. Лимиты памяти и хранение

| Контейнер | Лимит |
|---|---|
| grafana | 256 МБ |
| prometheus | 192 МБ |
| node-exporter | 48 МБ |
| blackbox | 48 МБ |
| postgres-exporter | 48 МБ |
| **Итого** | **592 МБ** |

После первого запуска смотрим `docker stats` за сутки. Если контейнер упирается в лимит, перераспределяем в пределах 600 МБ. Prometheus: `--storage.tsdb.retention.time=30d`, `--storage.tsdb.retention.size=1GB`, опрос раз в 30 секунд.

### 10. Логи

Все контейнеры мониторинга пишут в journald, как приложение (`tag={{.Name}}`, поля проекта и сервиса). `logs.sh` понимает окружение `monitoring` (`grafana`, `prometheus`, `node-exporter`, `blackbox`, `all`), а `logs.sh prod postgres-exporter` показывает сборщик базы. Фильтр rsyslog дополняется именами `monitoring-…` и `prod-postgres-exporter-…`.

### 11. Версии

Образы с точными тегами последних стабильных версий на момент реализации (проверить по страницам выпусков): `grafana/grafana`, `prom/prometheus`, `prom/node-exporter`, `prom/blackbox-exporter`, `prometheuscommunity/postgres-exporter`. Тянутся с Docker Hub: с сервера он доступен.

### 12. Внешняя проверка - UptimeRobot, руками

Пользователь регистрируется в UptimeRobot и заводит проверку HTTPS `https://app.whobook.ru/health` раз в 5 минут с письмом на свою почту. В репозитории только инструкция в README. Условия бесплатного тарифа проверить при настройке.

### 13. Проверка без автотестов

Код приложения не меняется. По CLAUDE.md сервер, скрипты выкатки и CI проверяются настоящей выкаткой, без автотестов. Поэтому «тест» каждого сценария - ручная проверка на сервере, она записана в tasks.md рядом со сценарием. До PR настройки проверяются локально в Docker: `promtool check config`, Grafana стартует с этими файлами provisioning без ошибок. Пороги тревог, которые нельзя вызвать безопасно (диск, память, процессор, сертификат, база прода), проверяем временной копией правила с порогом, который уже выполняется: письмо пришло → копию удаляем.

## Risks / Trade-offs

- [Упала Grafana - писем нет вовсе] → `restart: unless-stopped`; Deploy prod проверяет, что Grafana работает; внешняя проверка видит хотя бы недоступность сайта. Следующий шаг, если понадобится: сигнал «я жив» во внешний сервис (не в этой фиче).
- [Память: мониторинг плюс выкатка плюс нагрузка] → жёсткие лимиты, в сумме 592 МБ; тревога «мало памяти» срабатывает раньше, чем система начнёт закрывать процессы.
- [Сборщик базы ходит под владельцем базы прода] → он только читает статистику, порт только на 127.0.0.1 хоста. Отдельная роль только для чтения - позже, если понадобится.
- [Любой процесс на сервере может представиться Grafana кем угодно через заголовок] → Grafana доверяет заголовку только с 127.0.0.1, слушает только 127.0.0.1; контейнеры приложения в своей сети 127.0.0.1 хоста не видят. На сервере работаем только мы.
- [Плановые работы дают письма: `restore.sh` и пересоздание базы стенда останавливают приложение] → это ожидаемо; в README - как заглушить тревогу в Grafana на время работ.
- [Docker Hub недоступен при обновлении] → шаг «Update monitoring» красный, работающий мониторинг и приложение не тронуты, Deploy prod можно перезапустить.
- [После пересоздания Grafana может повторить письмо о тревоге, которая уже горит] → редкий лишний дубль, состояние тревог хранится в томе.
- [До merge проверить на сервере нельзя: мониторинг ставит Deploy prod, его запускает человек] → локальная проверка настроек до PR; первая настоящая проверка - после merge, по шагам из tasks.md.

## Migration Plan

1. PR, зелёный CI, merge. Deploy staging проходит как обычно: профиль сборщика базы на стенде выключен.
2. Пользователь: ключ Resend `monitoring`, строки `.env` мониторинга (команды дам в README, ключ вводится без вывода на экран).
3. Пользователь: `setup.sh` через sudo - сайт grafana.whobook.ru, сертификат, пароль Grafana, папка мониторинга, фильтр rsyslog.
4. Пользователь: Deploy prod - приложение со сборщиком базы, затем шаг «Update monitoring».
5. Агент: проверки по tasks.md. Остановку приложения стенда для проверки письма - только с согласия пользователя.
6. Пользователь: UptimeRobot.

Выключить мониторинг: `docker compose -p monitoring down` под `deploy` (данные в томах остаются), приложение не затронуто. Убрать совсем - откатить PR, затем остановить контейнеры той же командой (удалить тома - только с согласия пользователя).
