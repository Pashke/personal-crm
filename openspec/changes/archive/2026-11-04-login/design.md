# Design

## Context

Зачем - см. proposal.md, что именно должно работать - см. specs/user-auth, specs/data-ownership и specs/contact-groups.

Что есть сейчас:

- Таблицы `contacts`, `notes`, `groups`, `contact_groups`. Владельца нет ни у одной записи. Уникальный индекс `groups_name_lower_idx` по `lower(name)` - на всю базу. Миграции `drizzle/0000`-`0003`; `0003_default_groups` вставляет пять готовых групп, поэтому даже свежая база не пустая.
- Чтение - `src/lib/contacts.ts`, `src/lib/groups.ts`; запись - серверные действия `src/app/actions.ts`, `src/app/groups/actions.ts`. Ни одна функция не знает, кто спрашивает.
- Шапка - в `src/app/layout.tsx`, общая для всех страниц. Несуществующий контакт - общий `src/app/not-found.tsx` («Такой страницы нет»).
- На сервере миграции применяет разовый контейнер `migrate` (`drizzle-kit migrate`) из того же образа, до старта новой версии; перед этим `deploy.sh` снимает бэкап. Образ кладёт `scripts/`, `src/db/`, `drizzle/`, но не `src/lib/`.
- Prod-база - тестовые 1000 контактов и пять групп. Репозиторий на GitHub публичный.
- Тесты: Vitest на тестовой базе `<POSTGRES_DB>_test` (таблицы очищаются перед каждым тестом, `next/cache` и `next/server` заменены заглушками); Playwright собирает приложение и запускает его на порту 3100 с той же базой. CI поднимает Postgres из `docker-compose.yml`.

## Goals / Non-Goals

**Goals:**

- Кто спрашивает - решает только сервер: каждая функция чтения и записи получает пользователя явным параметром, без него код не собирается.
- Почта владельца не попадает в git: её даёт `.env`.
- Миграция данных атомарна: либо у всех записей появился владелец, либо база осталась прежней и новая версия не стартовала.
- Каждый сценарий спеки проверен тестом: серверная логика - Vitest на настоящей базе и настоящем Better Auth, путь человека - e2e через настоящую Mailpit, без моков.

**Non-Goals:**

- Защита от перебора на уровне nginx, капча.
- Чистка старых сеансов и пользователей, которые ни разу не вошли.
- Тексты писем на разных языках, HTML-шаблонизатор для писем.

## Decisions

### 1. Better Auth: таблицы и настройки

Сверено с исходниками `better-auth` 1.7.16 (вышла 2026-11-03; pnpm пустит её после 2026-11-04 ~21:30 UTC, до этого - 1.7.15 с той же логикой ниже).

- Таблицы Better Auth во множественном числе, как наши: `users`, `sessions`, `accounts`, `verifications` (`usePlural: true` в Drizzle-адаптере, ключи схемы - те же имена). Схему генерирует CLI Better Auth - теперь это npm-пакет `auth` (`pnpm dlx auth@<версия> generate`, `@better-auth/cli` устарел) - в `src/db/auth-schema.ts`, `src/db/schema.ts` его переэкспортирует; миграцию делает `drizzle-kit generate`, как раньше. CLI не загружает файл с `import "server-only"`, поэтому для него - отдельный маленький конфиг без `server-only`, который зовёт ту же фабрику `createAuth` (см. ниже) с Drizzle без соединения. Время в сгенерированной схеме - `timestamp` без пояса; меняем на `withTimezone: true`, как в наших таблицах (Date-режим Drizzle тот же, тесты сроков это проверяют). Своих колонок в таблицы Better Auth не добавляем: Better Auth сверяет схему при старте (`validateSchema`).
- Идентификаторы пользователей - текст из 32 символов, его генерирует Better Auth. Свои таблицы оставляют числовые id.
- Магическая ссылка: `expiresIn` - 15 минут (900 секунд; по умолчанию 5 минут). Ссылка одноразовая сама: Better Auth гасит её при первой проверке (`allowedAttempts` устарел и не нужен). Прежние ссылки Better Auth сама не отменяет - это делаем мы (решение 5). Любая негодная ссылка - неизвестная, просроченная, использованная - уводит на `errorCallbackURL` с `?error=INVALID_TOKEN`; другие коды (не удалось создать пользователя или сеанс) ведут туда же, и страница показывает тот же текст.
- Сеанс: `expiresIn` - 30 дней, `updateAge` - сутки: при заходе срок ставится заново на 30 дней вперёд, но не чаще раза в сутки, то есть после последнего захода вход живёт от 29 до 30 дней. Кэш сеанса в cookie (`cookieCache`) не включаем: с ним вышедший сеанс ещё до 5 минут работал бы на других устройствах.
- Встроенный лимит Better Auth (по IP, только для HTTP-запросов; для `/magic-link/verify` - 5 в минуту) оставляем. IP клиента - из `X-Real-IP`, который ставит наш nginx (`advanced.ipAddress.ipAddressHeaders`). Защищённые cookie (`Secure`, приставка `__Secure-`) - когда `BETTER_AUTH_URL` начинается с `https://`, то есть на сервере; на компьютере и в тестах - обычные.
- `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL` - из окружения. Объект `auth` создаётся при первом обращении, как `getDb()`: `next build` идёт без секретов. Настройки собраны в фабрике `createAuth(db)`: приложение зовёт её со своей базой, тест миграций - со временной.
- Обработчик Better Auth - `src/app/api/auth/[...all]/route.ts`. Запрос ссылки напрямую по HTTP (`/sign-in/magic-link`) выключен через `disabledPaths`: ссылку можно запросить только через наше серверное действие, где проверка почты и лимит. `disabledPaths` проверяется только в HTTP-роутере, вызов `auth.api.signInMagicLink` из сервера работает (исходник `api/index.ts`, `onRequest`); ему нужны заголовки запроса - передаём `await headers()`. Открытыми остаются проверка ссылки (`/magic-link/verify`) и служебные пути сеанса.
- Плагин `nextCookies()`, последним в списке, - чтобы серверные действия ставили и стирали cookie входа.
- Альтернатива - свой вход по ссылке без библиотеки. Отказались: Better Auth и MagicLink заданы в постановке, а сеансы и cookie - то место, где легко ошибиться самому.

### 2. Владелец у контактов и групп

- `contacts.user_id` и `groups.user_id` - text NOT NULL, ссылка на `users.id` без каскада: случайное удаление пользователя руками не сотрёт его контакты, база не даст. Индексы по `user_id`.
- Уникальность названия группы - `(user_id, lower(name))` вместо `lower(name)`. Вставка новых групп из формы контакта (`onConflictDoNothing`) и поиск существующих по названию - тоже в пределах пользователя.
- У заметок и `contact_groups` своего владельца нет: заметка принадлежит владельцу контакта, связь - владельцу контакта и группы. Запись связей выбирает группы только этого пользователя, так что чужая группа к контакту не попадёт.
- Альтернатива - `user_id` и у заметок. Отказались: дублирует владельца контакта и может с ним разойтись.

### 3. Каждая функция данных получает пользователя

- `listContacts(userId, query, groupId)`, `countContacts(userId)`, `listDueContacts(userId, groupId)`, `getContact(userId, id)`, `listNotes(userId, contactId)`, `listGroups(userId)`, `listContactGroups(userId, contactId)`, `setContactGroups(tx, userId, ...)`: в каждом запросе условие `user_id = $userId`, у заметок и групп контакта - через контакт.
- Записи - тем же условием в самом запросе, а не отдельной проверкой «до»: `update ... where id = $id and user_id = $userId` и т. п. Чужой id ведёт себя как несуществующий: 0 строк - тот же ответ, что сейчас для удалённого. Заметка добавляется только если контакт свой (вставка с условием на контакт в той же транзакции); отмена быстрой заметки удаляет заметку только своего контакта.
- Альтернатива - Row Level Security в Postgres. Отказались: требует отдельной роли и настройки соединения на каждый запрос; явный параметр проще проверить тестом и типами.

### 4. Кто вошёл - `src/lib/session.ts`

- `getCurrentUser()` - сеанс из cookie запроса через Better Auth (`auth.api.getSession` с заголовками запроса), один раз за запрос (React `cache`). `requireUser()` - то же, а без входа `redirect("/login")`.
- Каждая страница приложения и каждое серверное действие первым делом зовут `requireUser()` и передают `user.id` дальше. Это и есть защита.
- `src/proxy.ts` (в Next.js 16 так называется бывший middleware, работает в Node.js) нужен ради срока входа: Better Auth с `nextCookies()` не продлевает сеанс, когда его спрашивает серверный компонент страницы, - тот не может поставить cookie. Значит, простые заходы на страницы срок бы не продлевали, и вход кончался бы через 30 дней после входа, а не после последнего захода. Proxy на каждый запрос к страницам приложения спрашивает сеанс у Better Auth так, чтобы тот продлил срок (с `returnHeaders`), и переносит его `Set-Cookie` в ответ. Для этого у proxy свой экземпляр Better Auth без `nextCookies()` (`getProxyAuth`): плагин читает заголовки запроса через `next/headers`, и при переходах внутри приложения (`RSC: 1`) продление пропускалось бы. Сеанса нет - перенаправляет на `/login`; запрос серверного действия без сеанса пропускает дальше - действие само уводит на вход. Пропускает `/login`, `/login/expired`, `/api/auth/...`, `/health` и статику.
- Альтернатива для продления - запрос `/api/auth/get-session` из браузера на каждой странице. Отказались: лишний запрос из браузера и продление зависело бы от JavaScript на странице.
- Страницы приложения переезжают в группу маршрутов `src/app/(app)/` со своей разметкой: шапка с «Личная CRM», «Группы», почтой и «Выйти». Страницы входа - в `src/app/(auth)/` с шапкой из одного «Личная CRM». Корневой `layout.tsx` оставляет шрифты, рамку и `Toaster`. Адреса страниц не меняются.
- «Выйти» - форма с серверным действием: `auth.api.signOut` удаляет только этот сеанс, затем `redirect("/login")`.

### 5. Запрос ссылки - серверное действие `requestSignInLink`

Порядок, всё под одной транзакцией с `pg_advisory_xact_lock` по почте, чтобы два одновременных запроса на одну почту шли по очереди:

1. Почта: `trim`, нижний регистр, проверка адреса (zod `z.email()`, до 254 символов). Неверная - «Проверь адрес почты», дальше не идём. Та же функция нормализации - в миграции почты владельца и в демо-данных.
2. Лимит: таблица `sign_in_emails` (`email`, `sent_at`). Строки старше 10 минут удаляются, по почте считается число строк. 3 и больше - «Слишком часто, попробуй через несколько минут», ничего не меняется.
3. Прежние ссылки этой почты удаляются из `verifications`. Отбор - по полю `value`, где Better Auth хранит JSON `{"type":"magic-link","email":...}`: `value::jsonb->>'type' = 'magic-link'` и `value::jsonb->>'email' = <почта>`. Не по `identifier`: там токен, а его Better Auth может хранить и хешем. Почта в `value` - ровно та, что мы передали, а мы передаём уже нормализованную.
4. `auth.api.signInMagicLink` с `callbackURL: "/"` и `errorCallbackURL: "/login/expired"`; Better Auth сначала создаёт ссылку в `verifications` (своим соединением), потом ждёт наш `sendMagicLink`, а тот отправляет письмо. Ошибка отправки возвращается к нам.
5. Письмо ушло - строка в `sign_in_emails`, транзакция фиксируется, ответ «Ссылка для входа отправлена на <почта>». Не ушло - транзакция откатывается (удаление прежних ссылок отменяется, попытка не считается), ответ «Не удалось отправить письмо. Попробуй ещё раз.». Созданная Better Auth ссылка остаётся в базе, но её никто не получил, и через 15 минут она устареет.

- Альтернатива для шага 3 - хук Better Auth `databaseHooks.verification.create.after`, который удаляет остальные ссылки почты. Отказались: он сработал бы и тогда, когда письмо потом не ушло, и человек остался бы без рабочей ссылки.

- Таблица `sign_in_emails` хранит почту не дольше 10 минут после письма: старые строки удаляются при каждом запросе.
- Альтернатива - встроенный лимит Better Auth. Не подходит: он считает запросы с одного IP, а нужно - письма на одну почту.

### 6. Страницы входа

- `/login`: по макету, вариант «Б. Обложка» (https://claude.ai/artifact/ToG5gdWDXejyzR6etkFsKR, файл `project/Cover.dc.html`, на телефоне - `CoverPhone.dc.html`). Внутри обычной рамки приложения - ряд с переносом (`flex-wrap`): слева заголовок `h1` «Люди, которых знаю лично» (Oswald, как заголовки страниц, но крупнее), текст и строка шрифтом `font-hand`; справа панель с тонкой рамкой `border` и `h2` «Вход». На узком экране панель уходит под текст сама, без отдельной вёрстки для телефона. Форма на `useActionState`: поле `Input` с подписью `Label` «Почта», кнопка `Button` во всю ширину панели; ошибка - под полем, ответ об отправке - рамка с галочкой под кнопкой, ошибки лимита и отправки - текстом под кнопкой; введённая почта остаётся в поле. Цвета, шрифты и отступы - только дизайн-токены, значения в макете с ними совпадают. Заголовок вкладки - «Вход». Вошедший - `redirect("/")`.
- `/login/expired`: «Ссылка устарела, запроси новую» и кнопка «На страницу входа». Сюда Better Auth отправляет любую негодную ссылку, какой бы ни была причина.
- Обе страницы открыты без входа. После входа по ссылке Better Auth ставит cookie и перенаправляет на `/`.

### 7. Письма - Nodemailer, адрес сервера из `SMTP_URL`

- `src/lib/mail.ts`: транспорт Nodemailer из одной строки подключения `SMTP_URL`, создаётся при первом письме. На компьютере и в CI - `smtp://127.0.0.1:1025` (Mailpit), на сервере - `smtps://resend:<ключ>@smtp.resend.com:465`. Код один, решает настройка.
- `src/lib/sign-in-email.ts`: тема, HTML и текстовая версия письма - обычная функция от ссылки, её проверяет тест. Отправитель - константа `"Личная CRM" <noreply@mail.crm.whobook.ru>`: он одинаковый везде, в Mailpit адрес отправителя ничего не решает.
- Вид письма - по макету «Письмо 2. Как приложение, текст из письма 1» (https://claude.ai/artifact/ToG5gdWDXejyzR6etkFsKR, файл `project/MailDark.dc.html`): тёмно-зелёный фон, двойная золотая рамка, светлый текст, рыжая кнопка, ширина до 600 px, на телефоне сужается.
- HTML письма - таблицы со встроенными стилями: почтовые программы не понимают CSS-переменных, Tailwind и цвета `oklch()`. Цвета - копии значений из `src/app/tokens.css` в одном месте, с комментарием, откуда взяты; рыжий переведён в hex: `--color-rust` `oklch(0.55 0.15 38)` = `#b84a27`. Фон ставится и атрибутом `bgcolor`, и стилем - так его меньше перекрашивают.
- Шрифты: Oswald и PT Serif подключаются ссылкой на Google Fonts, но Gmail и многие программы их не грузят - там будут Arial и Georgia. Макет по умолчанию показывает именно этот вид.
- Строка для списка входящих («Ссылка для входа работает 15 минут») - скрытый текст в самом начале письма. Кнопка «Войти» - ссылка, оформленная кнопкой; та же ссылка повторяется текстом под ней.
- Текстовая версия письма - те же слова и ссылка обычным текстом.
- Альтернатива - API Resend вместо SMTP. Отказались: тогда на компьютере и в тестах был бы другой код отправки, а постановка требует одну библиотеку для обоих случаев.

### 8. Миграции: таблицы входа и владелец существующих данных

- `0004_*` - генерируется `drizzle-kit generate`: таблицы Better Auth и `sign_in_emails`. Только `CREATE TABLE` и `CREATE INDEX`.
- `0005_*` - генерируется и правится руками, это миграция, меняющая данные (показать вам до merge):
  1. `user_id` в `contacts` и `groups` - сначала без NOT NULL;
  2. если в `contacts` или `groups` есть строки: почта владельца берётся из настройки соединения `crm.owner_email`; её нет - `RAISE EXCEPTION`; пользователь с этой почтой создаётся (если его ещё нет), все контакты и группы получают его id;
  3. NOT NULL, ссылки на `users`, индексы, новый уникальный индекс групп вместо старого.
- Почту в настройку соединения кладёт `drizzle.config.ts`: читает `OWNER_EMAIL`, нормализует и проверяет той же функцией, что форма входа (она лежит в `src/db/`, её видит и образ), и ставит `PGOPTIONS="-c crm.owner_email=<почта>"`. Драйвер `pg` берёт `PGOPTIONS` из окружения, если параметр не задан в коде (проверено в `pg@8.23.1`, `connection-parameters.js`). Почта задана, но неверная - `drizzle-kit migrate` падает до соединения с базой. Тестовые `applyMigrations` передают тот же параметр в `options` пула напрямую.
- Команда миграций остаётся `drizzle-kit migrate` - и в `pnpm db:migrate`, и в сервисе `migrate` в `deploy/compose.yaml`, ему добавляется только `OWNER_EMAIL`. Это важно для отката: `rollback.sh` запускает миграции прошлой версии с новым `compose.yaml`, а в старом образе нет никаких новых скриптов.
- Мигратор Drizzle проводит все новые миграции одной транзакцией (`pg-core/dialect.js`, `migrate`): упала `0005` - откатывается и `0004`, база как до выкатки.
- Почему так: почта не попадает в публичный git, а миграция остаётся одним SQL-файлом, который можно прочитать и проверить тестом. Альтернативы: почта прямо в SQL - видна на GitHub; свой скрипт миграций вместо `drizzle-kit migrate` - ломает откат на старые образы; отдельный шаг «назначить владельца» после миграций - между шагами база была бы с записями без владельца, а NOT NULL пришлось бы ставить ещё одной миграцией.
- Свежая база тоже не пустая (пять групп из `0003`), поэтому `OWNER_EMAIL` нужен для каждой базы, где ещё не применена `0005`: на компьютере, в CI, на сервере. Тесты передают тестовую почту владельца.

### 9. Демо-данные

`scripts/seed.ts` берёт `OWNER_EMAIL`, находит пользователя с этой почтой или создаёт его, проверяет, что у него нет контактов, и пишет контакты, заметки и членство в группах на него, в его группы. Логика - в функции, которую можно вызвать из теста; `main()` только читает настройки и зовёт её.

### 10. Новые тексты интерфейса

- «Контакт не найден»: `src/app/(app)/contacts/[id]/not-found.tsx` - заголовок «Контакт не найден», текст «Возможно, контакт удалён или в адресе опечатка.», кнопка «К списку контактов». Его же видит страница «Изменить» - Next.js берёт ближайший `not-found`.
- Пустой список: «Добавь первый контакт» - ссылка на `/contacts/new`, вместо прежнего текста.
- Шапка на ширине телефона: почта обрезается многоточием, «Выйти» всегда видна.

### 11. Настройки окружения

| Переменная | Компьютер (`.env`) | CI | Сервер |
|---|---|---|---|
| `OWNER_EMAIL` | ваша почта | тестовая | `.env`, ваша почта |
| `BETTER_AUTH_SECRET` | случайная строка | случайная на прогон | `.env`, случайная строка |
| `BETTER_AUTH_URL` | `http://localhost:3000` | `http://127.0.0.1:3100` (задаёт `playwright.config.ts`) | `https://app.whobook.ru` прямо в `deploy/compose.yaml` - не секрет |
| `SMTP_URL` | `smtp://127.0.0.1:1025` | `smtp://127.0.0.1:1025` | `.env`, с ключом Resend |

- В `deploy/compose.yaml` обязательные переменные - через `${VAR:?...}`: если строки в `.env` на сервере нет, выкатка останавливается на первом же шаге, до бэкапа, ничего не меняя.
- Mailpit в `docker-compose.yml`: SMTP `127.0.0.1:1025`, страница с письмами `http://localhost:8025`, только на localhost. Письма живут в памяти Mailpit до его перезапуска.

### 12. Тесты

- **Vitest, серверная часть.** Текущий пользователь задаётся в тесте (заглушка `src/lib/session.ts`); перед каждым тестом очищаются и таблицы входа, и создаётся пользователь A по умолчанию, так что прежние тесты работают как A почти без правок. Отправка писем заменена ловушкой, которая запоминает письма. Better Auth - настоящий, на тестовой базе: ссылку из пойманного письма открываем через `auth.handler(new Request(url))` и по ответу видим, впустила ли она, - так проверяются «один раз», «15 минут» (срок двигаем в базе), «новая отменяет прежние», «испорченная». Срок входа - тоже через базу: сдвигаем время сеанса и спрашиваем сеанс по cookie.
- **Vitest, данные двух пользователей.** Для каждой функции чтения и каждого действия - сценарий с чужим id из spec `data-ownership`.
- **Vitest, миграции.** База до `0004` с контактами, заметками, группами и связями → все миграции с почтой владельца → число строк и поля те же, у всех владелец с нормализованной почтой; без почты - ошибка, база прежняя; свежая база - пять групп у владельца.
- **Proxy, Vitest.** Функцию `proxy` зовём с настоящим `NextRequest` и cookie настоящего сеанса: сеанс суточной давности - в ответе `Set-Cookie`, срок в базе сдвинулся на 30 дней от сейчас (сценарий «Заходит регулярно»); без cookie - перенаправление на `/login`.
- **e2e, без моков.** Настоящая сборка, настоящая Mailpit: тест запрашивает ссылку в форме, берёт письмо через API Mailpit (`/api/v1/search?query=to:"<почта>"` - новое первым, `/api/v1/message/<id>`), открывает ссылку. `pnpm start` работает в режиме production, где включён встроенный лимит Better Auth по IP; без `X-Real-IP` все тесты попали бы в одну корзину «5 проверок ссылки в минуту». Поэтому браузер в каждом тесте посылает свой `X-Real-IP`, как nginx на сервере. Поиск Mailpit по `to:` ищет подстроку - у каждого теста своя уникальная почта. Новый `e2e/login.spec.ts`: главный сценарий входа и критерий успеха с A и B, ошибки формы, письмо, «Ссылка устарела», выход, два устройства. Существующие e2e перед сценарием входят под пользователем тем же помощником; тестовые данные пишутся на этого пользователя. Каждый тест - со своей почтой, чтобы не упереться в лимит писем.
- **CI:** Postgres и Mailpit из `docker-compose.yml`, `BETTER_AUTH_SECRET` случайный на каждый прогон, `OWNER_EMAIL` тестовый.

## Risks / Trade-offs

- [Хостинг закрывает исходящие SMTP-порты, письма с сервера не уходят] → до merge проверить с сервера соединение с `smtp.resend.com:465`; если закрыто - порт 2465 у Resend или вопрос к хостингу. После выкатки - письмо на свою почту руками.
- [Домен `mail.crm.whobook.ru` не подтверждён в Resend - письма отклоняются] → вы заводите домен и DNS-записи до merge; выкатка без этого не сломает данные, но войти будет нельзя.
- [Без `OWNER_EMAIL` или с опечаткой в нём данные достанутся не тому] → скрипт проверяет формат и падает; после выкатки вы входите на свою почту и видите свои контакты; если не видите - откат вместе с базой из бэкапа.
- [Better Auth меняет устройство таблицы `verifications`, и удаление прежних ссылок по почте перестаёт работать] → тест «новая отменяет прежние» на настоящем Better Auth упадёт при обновлении библиотеки.
- [Ссылка в письме ведёт на `BETTER_AUTH_URL`: на компьютере это `localhost`, с телефона она не откроется] → проверять вход с компьютера; для телефона - временно указать в `.env` адрес компьютера в сети в `BETTER_AUTH_URL` (Better Auth доверяет только этому адресу).
- [Почтовые сервисы с «проверкой ссылок» (бывает в корпоративной почте) сами открывают ссылку из письма, и одноразовая ссылка сгорает до клика человека] → по постановке ссылка одноразовая; человек увидит «Ссылка устарела» и запросит новую. Если станет мешать - вернёмся к этому отдельно.
- [`better-auth` 1.7.16 вышла меньше суток назад, pnpm её пока не ставит] → к началу реализации, скорее всего, уже можно; если нет - спросить вас, взять ли 1.7.15 (исправления 1.7.16 касаются того, чего у нас нет: кэша сеанса в cookie, OAuth, passkey).
- [Тёмное письмо: некоторые почтовые программы в тёмной или светлой теме сами перекрашивают цвета, кнопка или текст могут стать менее заметными] → фон и цвета заданы и атрибутами, и стилями; после выкатки вы смотрите письмо в своей почте на компьютере и телефоне; если поплывёт - переделаем отдельной правкой.
- [Proxy спрашивает сеанс в базе на каждый запрос страницы] → один запрос по уникальному индексу; для личного приложения нагрузка ничтожная.
- [Транзакция держится, пока уходит письмо] → блокировка только по одной почте, другие почты не ждут; при сбое SMTP Nodemailer обрывает соединение по таймауту.
- [Миграция `0005` меняет все строки `contacts` и `groups`] → на 1000 контактах это доли секунды; перед выкаткой бэкап, как всегда.
- [Старая версия приложения после отката на новой схеме показывала бы всем все контакты] → откат только вместе: база из бэкапа перед выкаткой и прошлая версия (README).

## Migration Plan

До merge (вы):

1. Resend: аккаунт, домен `mail.crm.whobook.ru`, DNS-записи у регистратора, домен подтверждён; ключ с правом отправки.
2. На сервере в `/home/deploy/personal-crm/.env` - строки `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `SMTP_URL` (точные строки и команду для секрета скажу).
3. На компьютере в `.env` - те же строки с локальными значениями.

До merge (я): показать SQL `0005`; проверить с сервера порт Resend; записать число контактов, заметок, групп и связей в prod-базе.

Выкатка - обычная: бэкап → миграции нашим скриптом → новая версия → smoke `/health`. Затем: число строк то же; вход на вашу почту - ваши контакты на месте; вход на вторую почту - пустой список.

Откат - только вручную и только вместе: `restore.sh` с бэкапом, снятым этой выкаткой, и `rollback.sh` на прошлую версию (README, «Вернуть всё как было до неудачной выкатки»).
