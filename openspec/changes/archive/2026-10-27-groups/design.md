# Design

## Context

Зачем — см. proposal.md, что именно должно работать — см. specs/contact-groups/spec.md и specs/keep-in-touch/spec.md.

Что есть сейчас:

- Таблицы `contacts` и `notes` (`notes.contact_id` → `contacts.id`, ON DELETE CASCADE). Миграции — `drizzle/0000_init.sql`, `drizzle/0001_contact_frequency.sql`; на сервере их применяет разовый контейнер `drizzle-kit migrate` до старта нового образа.
- Образ кладёт `src/db/` целиком (нужен `scripts/seed.ts`), но не кладёт `src/lib/`: `src/db/schema.ts` не может импортировать из `src/lib/`.
- Все страницы читают базу на каждый запрос (`connection()` в `src/lib/contacts.ts`). Серверные действия — в `src/app/actions.ts`, проверка ввода — zod в `src/lib/contact-schema.ts`, тексты ошибок для людей — по-русски, в логах только технические поля (`describeError`).
- Главная: `?q=` — поиск (`SearchBox` пишет его в адрес через `router.replace`), `listContacts(query)`, `countContacts()`, `listDueContacts()`. Сортировка по имени — `collate "ru-x-icu"`, поиск — `ilike`, кириллица в нём уже работает без учёта регистра.
- Форма контакта — `ContactForm` на `useActionState`; «Как часто общаться» — обычные радиокнопки, оформленные как ряд переключателей, чтобы после ошибки React сам восстанавливал выбор.
- Удаление контакта — `DeleteContactButton` с окном подтверждения из shadcn/ui (`AlertDialog`).
- Тестов в проекте нет. В CLAUDE.md в стеке уже есть Vitest и Playwright; e2e и CI — отдельная фича позже.

## Goals / Non-Goals

**Goals:**

- Состав групп хранится в одном месте — таблице связей; ни в контакте, ни в группе нет копий.
- Уникальность названия без учёта регистра и целостность связей обеспечивает база, а не только код.
- Каждый сценарий спеки проверяется тестом Vitest на настоящей тестовой базе; для этого логика, которую видно на экране (тексты, адреса, разбор адреса), вынесена в обычные функции.
- Существующие контакты и выкатка не ломаются: миграции только добавляют.

**Non-Goals:**

- Тесты компонентов в браузерном окружении (jsdom, Testing Library) — экраны проверит e2e, когда настроим Playwright.
- CI — отдельная фича.

## Decisions

### 1. Две новые таблицы: `groups` и `contact_groups`

- `groups`: `id` (identity), `name` text NOT NULL, `created_at`. Уникальный индекс по выражению `lower(name)` — двух «Теннис»/«теннис» база не пустит, даже если два запроса придут одновременно.
- `contact_groups`: `contact_id` → `contacts.id` и `group_id` → `groups.id`, оба ON DELETE CASCADE, первичный ключ `(contact_id, group_id)` — контакт не может попасть в группу дважды. Отдельный индекс по `group_id` — для фильтра и подсчёта контактов в группе.
- Порядок групп «в порядке создания» = по `id`. Отдельной колонки порядка нет: ручной порядок не входит в фичу.
- Удаление контакта или группы само убирает связи (CASCADE) — как сейчас заметки при удалении контакта.
- Альтернатива: массив названий групп в колонке контакта. Отказались: переименование и удаление группы пришлось бы проводить по всем контактам, база не проверяла бы, что такая группа есть.
- `lower()` для кириллицы зависит от локали базы; та же локаль уже даёт `ilike` без учёта регистра для русских имён. Тест на «теннис»/«Теннис» на настоящем Postgres это подтверждает.

### 2. Пять готовых групп — отдельной миграцией с данными

`pnpm db:generate` создаёт `0002_*` с таблицами и индексами. Вторая миграция `0003_default_groups` создаётся `drizzle-kit generate --custom` и содержит один `INSERT` пяти названий в нужном порядке — `id` идут подряд, значит и порядок правильный.

- Почему миграция, а не сид: группы нужны и на сервере, а сид — только тестовые данные на пустой базе.
- Почему не «создать при старте приложения, если групп нет»: удалил все группы — они вернулись бы сами. Миграция выполняется один раз.

### 3. Чтение групп

- Новый модуль `src/lib/groups.ts` (server-only): `listGroups()` — все группы с числом контактов, по `id`; `listContactGroups(contactId)` — группы контакта (`id`, название) по `id`.
- `listContacts(query, groupId?)`: фильтр по группе — `exists` по `contact_groups`; в каждой строке — названия групп контакта массивом в общем порядке (подзапрос с `array_agg(... order by groups.id)`). Порядок строк прежний.
- `listDueContacts(groupId?)`: тот же `exists`-фильтр, остальное без изменений.
- `countContacts()` не меняется: M в «Найдено N из M» — все контакты.
- Главная сначала читает `listGroups()` (он нужен для ряда фильтров), по нему проверяет `?group=`, а потом параллельно — список, счётчик и «Пора связаться» с проверенным id.

### 4. Выбранная группа — параметр `?group=<id>` в адресе

- Разбор — обычная функция `resolveSelectedGroup(param, groups)`: не число или такой группы нет — `null`, то есть «Все». Число разбирается так же, как id контакта сейчас (`parseContactId` обобщается до `parseId`).
- Адреса главной собирает одна функция `homeHref({ q, groupId })`: её используют кнопки фильтра, ссылки со страницы «Группы» и со страницы контакта, и `SearchBox`.
- Кнопки фильтра — обычные ссылки (`<Link>`, без прокрутки наверх): переход добавляет запись в историю, поэтому «Назад» возвращает прежнюю группу. Текст поиска при смене группы сохраняется.
- `SearchBox` получает выбранную группу и строит адрес через `homeHref`: ввод и очистка поиска не теряют `group`. Поиск по-прежнему `router.replace` — каждая буква не попадает в историю.
- Почему id, а не название: переименование не ломает сохранённые ссылки, в адресе нет кириллицы и экранирования.

### 5. Тексты на экране — в обычных функциях `src/lib/format.ts`

Счётчик («Найдено 3 из 1 000» / «1 000 контактов»), пустые состояния («В группе «Аналитики» пока никого нет», «Никого не нашлось по запросу «ив» в группе «Теннис»»), число контактов на странице «Группы» («3 контакта», «нет контактов»), строка групп («Друзья, Теннис») и тексты окна удаления собираются функциями. Страницы только вызывают их. Так тексты проверяются тестами Vitest без отрисовки страниц.

### 6. Проверка названия — общая zod-схема для браузера и сервера

`src/lib/group-schema.ts`: `groupNameSchema` — `trim`, от 1 до 50 символов, сообщения «Укажите название группы», «Слишком длинное название». Её используют страница «Группы», поле новой группы в форме контакта (сразу при вводе) и сервер (всегда, для подменённых запросов). Повтор названия проверяет база (решение 1), сервер переводит ошибку уникальности (SQLSTATE 23505, новая функция `isUniqueViolation` рядом с `isForeignKeyViolation`) в «Такая группа уже есть».

### 7. Действия со страницы «Группы» — `src/app/groups/actions.ts`

- `createGroup(prev, formData)`: проверка схемой → `INSERT`; повтор → «Такая группа уже есть», введённый текст возвращается в поле. Успех — форма очищается.
- `renameGroup(id, prev, formData)`: проверка → `UPDATE ... WHERE id`; повтор → «Такая группа уже есть»; ноль строк → «Группа не найдена — возможно, её удалили.». Смена регистра той же группы проходит: уникальный индекс не конфликтует со своей же строкой.
- `deleteGroup(id)`: `DELETE ... WHERE id`; ноль строк — тоже успех, как при удалении контакта.
- Сбой базы — «Не удалось сохранить группу. Попробуйте ещё раз.» / «Не удалось удалить группу. Попробуйте ещё раз.», в лог — только `describeError`, без названий.
- Названия групп видны на всех страницах, поэтому после изменения — `revalidatePath("/", "layout")`.

### 8. Группы контакта сохраняются вместе с контактом, в одной транзакции

Форма отправляет `groupIds` (отмеченные существующие группы, несколько значений) и `newGroups` (названия новых, несколько значений).

- `contactSchema` дополняется этими полями. Значения `groupIds`, которые не разбираются как id, отбрасываются. Каждое из `newGroups` проверяется `groupNameSchema`; ошибка — сообщение под полем «Группы», контакт не сохраняется и новые группы не создаются.
- `createContact` и `updateContact` пишут в одной транзакции: контакт → `INSERT` новых названий `ON CONFLICT DO NOTHING` → id групп по `lower(name)` (так название существующей группы попадает в неё же) → связи заменяются: старые удаляются, новые вставляются через `INSERT ... SELECT id FROM groups WHERE id = ANY(...)`. Группы, которых уже нет, просто не вставятся — без ошибки.
- При ошибке проверки сервер возвращает `groupIds` и `newGroups` вместе с остальными полями, форма показывает их снова.
- Логика общая для создания и изменения — функция в `src/lib/groups.ts`, принимающая транзакцию.
- Альтернатива: создавать новую группу сразу по кнопке в форме отдельным запросом. Отказались: «Отмена» оставляла бы созданные группы, а спека требует, чтобы до сохранения контакта группы не было.

### 9. Поле «Группы» в форме контакта

- Страницы «Новый контакт» и «Изменить контакт» передают в `ContactForm` список групп; «Изменить» — ещё и id групп контакта в `initialValues`.
- Переключатели — обычные `<input type="checkbox" name="groupIds">`, оформленные как кнопки «Как часто общаться»: после ошибки React сам вернёт `defaultChecked`.
- Новая группа: поле «Новая группа» и кнопка «Добавить» под переключателями. Enter в этом поле добавляет группу и не отправляет форму. Добавленные группы — переключатели с hidden-полем `newGroups`; снять отметку — убрать группу из списка. Решение «добавить / отметить существующую / ошибка» принимает обычная функция `addPendingGroup(input, groups, pending)` — её проверяет тест.
- Стиль переключателя выносится в общий класс в `globals.css` (как `.contact-row`) и используется полем частоты, полем групп и фильтром на главной. Только дизайн-токены.

### 10. Главная

- Порядок сверху вниз: заголовок со счётчиком → ряд фильтров → «Пора связаться» → поиск → список. Фильтры стоят над блоком, потому что действуют и на блок, и на список.
- Ряд фильтров — `<nav aria-label="Группы">`, у выбранной ссылки `aria-current`; переносится на новые строки. Групп нет — ряда нет.
- Строка списка: группы — новым элементом в сетке `.contact-row`: на телефоне ещё одна мелкая строка, на компьютере — отдельная колонка между «Откуда знакомы» и телефоном. Обрезается многоточием, как остальные поля. Колонки выровнены и у контактов без групп.
- Строки блока «Пора связаться» не меняются.

### 11. Страница «Группы» и шапка

- `/groups`: заголовок «Группы», форма «Новая группа», список групп: название — ссылка на главную с группой, число контактов, «Переименовать», «Удалить». Нет групп — «Групп пока нет».
- Переименование — на месте: строка переключается в поле с «Сохранить» и «Отмена» (клиентский компонент с `useActionState`), Esc — как «Отмена».
- Удаление — компонент по образцу `DeleteContactButton`: окно подтверждения не закрывается, пока идёт удаление, ошибка показывается в окне.
- Шапка в `layout.tsx`: «Личная CRM» слева, «Группы» справа, тем же стилем.

### 12. Страница контакта

Строка «Группы» сразу после «Откуда знакомы»: названия через запятую, каждое — ссылка `homeHref({ groupId })`. Нет групп — прочерк, как у других пустых строк.

### 13. Тестовые данные

`scripts/seed.ts` берёт существующие группы (после миграций это пять готовых) и раскладывает контакты: примерно треть без групп, остальные в одной-двух случайных; родственники из «откуда знакомы» — в «Семья», тренер по теннису — в «Теннис». Групп нет — контакты без групп. Сид по-прежнему работает только на пустой базе.

### 14. Тесты: Vitest на отдельной тестовой базе

- Зависимость для разработки — `vitest`, последней стабильной версии на момент установки (сейчас 5.0.5). Других библиотек не нужно: без браузерного окружения, алиас `@/` — в настройках Vitest.
- `pnpm test` — один прогон (`vitest run`), `pnpm test:watch` — с перезапуском при правках.
- База — `<POSTGRES_DB>_test` в том же локальном Postgres из Docker, подключение из того же `.env`. Перед прогоном её пересоздают и применяют все миграции из `drizzle/` тем же механизмом, что на сервере. Защита: код тестов отказывается работать с базой, имя которой не заканчивается на `_test`, — рабочая база не пострадает.
- Перед каждым тестом таблицы очищаются (`TRUNCATE ... RESTART IDENTITY CASCADE`), тест сам создаёт нужные контакты и группы. Файлы идут по очереди: база одна.
- Серверные действия и запросы вызываются напрямую. Подменяется только то, что работает лишь внутри запроса Next.js: `revalidatePath` и `connection()` из `next/server` — пустые функции, `server-only` — пустой модуль. `redirect` бросает свою обычную ошибку, тест проверяет адрес в ней. База — настоящая.
- Сценарии «Готовые группы»: отдельная временная база, на неё — миграции до `0001`, затем контакты с заметками, затем остальные миграции; проверяем пять групп по порядку и неизменные контакты. Временная база удаляется после теста.
- Тесты лежат в `tests/`, названия на английском, у каждого — имя сценария из спеки. `tests/` и `vitest.config.mts` добавляются в `.dockerignore`: в образ они не нужны.
- Без серверной части остаются только сценарии, где всё решает браузер: ссылка в шапке, «Отмена» при переименовании, «Отмена» в окне удаления, «Отмена» формы, «Назад», ряд фильтров скрыт без групп. Их проверяем руками по README, e2e на них — в фиче с Playwright.

## Risks / Trade-offs

- [Тесты пересоздают базу] Ошибка в настройках могла бы стереть рабочие данные → проверка суффикса `_test` перед любым изменением; тесты запускаются только локально.
- [Тестам нужен Docker] Без запущенного Postgres `pnpm test` падает → в README: сначала `docker compose up -d --wait`; ошибка подключения говорит об этом прямо.
- [Группу удалили ровно в момент сохранения контакта] Между выбором id и вставкой связи группа может исчезнуть → вставка упадёт по внешнему ключу, пользователь увидит «Не удалось сохранить», повтор пройдёт без этой группы. Принято: шанс ничтожный.
- [Много групп] Ряд фильтров на телефоне занимает несколько строк и сдвигает список вниз → принято: для личной CRM групп немного; прокрутку ряда можно сделать позже.
- [Длинный список групп в строке] На узком экране обрезается многоточием → полный список виден на странице контакта.
- [Сид меняет данные] Новые случайные значения сдвигают последовательность faker → это тестовые данные, на реальную базу сид не действует.

## Migration Plan

1. `0002_*` (генерирует `pnpm db:generate`): таблицы `groups` и `contact_groups`, уникальный индекс `lower(name)`, индекс по `contact_groups.group_id`.
2. `0003_default_groups` (`drizzle-kit generate --custom`): пять готовых групп.
3. Выкатка как обычно: merge в main → образ → на сервере разовый контейнер применяет обе миграции → стартует новый образ → smoke `/health`.
4. Миграции только добавляют: контакты и заметки не трогаются. Старый образ о новых таблицах не знает и работает как раньше.
5. Откат — вручную, как принято: запустить предыдущий образ. Таблицы ему не мешают, удалять их не нужно; при следующей выкатке миграции не повторятся.
